If you publish GSX airport profiles, you can ship FlightStrips assignment with
one: a handler script beside your `.ini`. Pilots copy both files into their GSX
folder and fly. What they get is described in [GSX for pilots](/gsx/pilots/).

The work is in three parts:

1. **Map your scenery.** FlightStrips learns your stand names and pushback
   route labels. This is a change to the FlightStrips repository.
2. **Prepare the script.** Copy the shipped handler, rename it for your profile,
   and set one value.
3. **Test it, then publish it** alongside your profile.

## How it works

The script polls FlightStrips every five seconds:

```
GET https://api.flightstrips.dk/api/gsx/stand?callsign=XNO10&icao=EKCH&scenery=Simnord-Sonnich
```

FlightStrips looks up the strip for that callsign in the live session at that
airport. It translates what the controller assigned into your scenery's own
names, and answers with at most one of:

```json
{ "stand": "Gate A31", "pushback": null, "revision": "stand:Gate A31" }
{ "stand": null, "pushback": ["S1 Face N"], "revision": "push:S1 Face N" }
```

- **Arriving:** the script calls `selectGate()` with the stand.
- **Departing:** the script adds an **ATC Assigned** entry to the pushback menu,
  a copy of the route that reaches the assigned point.

The endpoint is public: GSX scripts can only make a plain GET request, with no
headers. It discloses nothing beyond what is already public on the VATSIM
datafeed. The details are in the [GSX stand feed](/dev/gsx-stand-feed/)
reference.

## 1. Map your scenery

Every add-on numbers stands and names routes its own way. What controllers call
`F91` is `Parking 91` in one EKCH scenery, and a push onto S1 facing north is
`S1 Face N` in exactly one profile. FlightStrips keeps that translation in
`backend/config/<icao>/gsx_sceneries.json`:

```json
{
  "icao": "EKCH",
  "gates": {
    "D2": {
      "Simnord-Sonnich": {
        "stand": "Gate D2",
        "points": {
          "S1": ["S1 Face N"],
          "S2": ["S2 Face S"],
          "S3": ["S3 Face N"],
          "R1": ["R1 Face N"]
        },
        "available": ["S2 Face S", "S3 Face N", "R1 Face N", "S1 Face N"]
      }
    }
  }
}
```

Read it as **gate → scenery → what your scenery calls it**:

| Field | What goes in it |
| --- | --- |
| Gate key (`D2`) | The stand as FlightStrips controllers know it. |
| Scenery key (`Simnord-Sonnich`) | A name for your scenery. Your script sends it as `SCENERY`. |
| `stand` | The name GSX's `selectGate()` resolves in your scenery. Omit it if it matches the gate key. |
| `points` | Each FlightStrips release point, mapped to every route label in your profile that reaches it. |
| `available` | Every route your profile offers at the stand. Only there to help whoever edits the file. |
| `review` | Optional free-text note about anything unresolved. Ignored by the server. |

<Steps>

1. **Find the stand in your `.ini`.** Each stand is a section such as
   `[gate d 2]`.

2. **Collect its route labels.** `pushbacklabels` holds the two default routes,
   left then right. Each `pushbackaddpos` entry adds one more, with its own
   `label`.

3. **Map each label to a release point.** A label such as `S1 Face N` is
   `<release point> Face <direction>`. The part before `Face` is the point a
   controller assigns. Copy the labels exactly: the server compares them
   ignoring case and extra spaces, nothing more.

4. **List both facings when a stand has both.** If a stand offers `Z2 Face E`
   and `Z2 Face W`, list both under `Z2`, preferred first. The script takes the
   first one the stand has.

5. **Open a pull request** against the FlightStrips repository with the new or
   changed file.

</Steps>

Anything unmapped degrades quietly. With an unknown scenery or unmapped point,
the stand is still published in the controller's own naming, and no pushback
point is sent.

## 2. Prepare the script

<Steps>

1. **Copy the shipped handler.** Start from the latest
   `gsx-client/EKCH-Simnord-Sonnich_handler.py` in the FlightStrips repository.
   It works for any airport and scenery: nothing in it is specific to EKCH
   apart from the two settings below.

2. **Name it after your profile.** GSX loads an airport script only when its
   name is the profile's name plus `_handler`:

   | Your profile | Your script |
   | --- | --- |
   | `EKCH-Simnord-Sonnich.ini` | `EKCH-Simnord-Sonnich_handler.py` |
   | `EGKK-MyScenery.ini` | `EGKK-MyScenery_handler.py` |

   A wrong name means the script never loads, and GSX gives no warning.

3. **Set the scenery key.** Near the top of the file:

   ```python
   API_BASE = "https://api.flightstrips.dk"
   SCENERY = "Simnord-Sonnich"
   ```

   `SCENERY` must match the scenery key you used in `gsx_sceneries.json`.
   Leave `API_BASE` on the production server unless your vACC runs its own
   FlightStrips instance.

</Steps>

### Settings

The defaults are what pilots should get. Change them only for a reason.

| Setting | Default | Effect |
| --- | --- | --- |
| `ATC_ENTRY_LABEL` | `ATC Assigned` | The menu entry's name before a point is assigned. |
| `ATC_ENTRY_LABEL_POINT` | `ATC Assigned: %s` | Its name once a point is assigned before the menu is built. Must start with `ATC_ENTRY_LABEL`. |
| `SHOW_ON_VDGS` | `True` | Also show `PUSH S1 FACE N` on the stand's docking display. |
| `POLL_INTERVAL_MS` | `5000` | How often the script asks FlightStrips. |
| `ANNOUNCE_WAITING` | `False` | Tell a pilot who calls the tug that no point is assigned yet. Off, because offline the pilot would wait for a point that never comes. |
| `ATC_ENTRY` | `True` | Turn off only to fall back to the older marking modes. |

## 3. Test it

You can fly the whole departure flow without a controller, using the mock
server in `gsx-client/mock/`. It answers like FlightStrips and lets you play the
controller.

<Steps>

1. **Start a mock server.** On Windows, the keyboard-driven one:

   ```powershell
   powershell -ExecutionPolicy Bypass -File gsx-client\mock\api-tui.ps1
   ```

   Edit `$Points` at the top to list route labels from the stand you will test
   at. The mock does not know which stand you are on.

2. **Point your installed script at it.** This copies your script into your GSX
   folder under its own filename, and sets `API_BASE`:

   ```bash
   gsx-client/mock/deploy.sh http://localhost:8787 path/to/EGKK-MyScenery_handler.py
   ```

   Leave out the second argument to deploy the EKCH script from the repository.

   Never commit a local `API_BASE`. Set it back to the production URL before
   you publish.

3. **Load the script.** Start the sim at your airport with the profile active.
   To reload the script without restarting, enable handler scripts with
   `enable_handler_scripts` in `%APPDATA%\Virtuali\CouatlAddons.ini`, then press
   `F5` in GSX's Handler Script Editor.

4. **Fly the departure checks.** Park at the stand you configured the mock for,
   and run each case:

   | Assign | When | Expect |
   | --- | --- | --- |
   | A route | Before the tug is called | An announcement. The menu is untouched until pushback is requested. |
   | A route | While the tug drives out | The entry is renamed `ATC Assigned: <route>`. Picking it pushes there. |
   | A route | With the direction menu on screen | The entry is still called `ATC Assigned`. Picking it pushes to the route. |
   | A route the stand lacks | Any time | `no route to it from this stand`. |
   | Reset | After assigning | The entry goes back to the scenery's first route. |

5. **Watch the log.** Every line the script writes starts with `[stands]`, in
   `%APPDATA%\Virtuali\Couatl.log`. A script with an error is skipped with a
   single `WARNING: airport handler script` line and nothing in the sim.

</Steps>

## Publish

- Ship the script next to the `.ini`, named for it, with `API_BASE` on the
  production URL.
- Link pilots to [GSX for pilots](/gsx/pilots/).
- Check that your scenery's mapping has been merged into FlightStrips. Until
  it is, pilots get stands in the controller's naming and no pushback point.

## If you change the script

GSX constrains airport scripts in ways that fail silently. Each of these has
already cost a test flight:

- **Reads of `getGate().pushbackAddPos` are copies.** Changing a dict read out
  of it does nothing. Write the whole list back, keeping its length and order.
- **Never remove routes, or write `getGate().pushback`, and leave it that way.**
  GSX reaches "Release parking brakes" and the tug never moves. Adding an entry
  is safe.
- **Never change the routes once the aircraft is moving.** The tug is driving
  them.
- **Labels are fixed once GSX shows the direction menu,** at departure state 5.
  Where an entry leads is not: GSX reads the routes again when the tug drives.
- **Builtins are restricted.** `globals()`, `setattr`, `vars` and `delattr` are
  not available.
- **Create attributes on `self` by plain assignment.** An attribute written
  through `self.__dict__` raises "not accessible from handler scripts" when it
  is read later.
- **Use `True`, not `TRUE`.** A typo like that is reported only as one warning
  line in the log.

Run the test suite before flying. It needs Python 3.7, the version GSX ships.
From `gsx-client/`:

```bash
docker run --rm -v "$PWD:/w" -w /w python:3.7-alpine \
  python mock/suite.py EKCH-Simnord-Sonnich_handler.py
```
