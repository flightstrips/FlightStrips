If you publish GSX airport profiles, you can ship FlightStrips assignment with
one: a handler script beside your `.ini`. Pilots copy both files into their GSX
folder and fly. What they get is described in [GSX for pilots](/gsx/pilots/).

It works with any GSX profile, and nothing has to be registered with
FlightStrips first:

- **Pushback points are matched by position, not by name.** FlightStrips knows
  where each release point is. The script picks your stand's route that ends
  there, whatever you call it. `S1 Face N` and `Release Point S1 (NORTH)` both
  work, and so does a name that's wrong.
- **Stands** are sent as the controller names them (`D2`). GSX matches that to
  your parking (`Gate D2`) by itself.

The work is in three parts:

1. **Add the script** to your profile: copy one ready-made block, as a new
   handler script or at the end of the one you already ship.
2. **Check your profile** against FlightStrips' release points.
3. **Test it, then publish it** alongside your profile.

## How it works

The script polls FlightStrips every five seconds:

```
GET https://api.flightstrips.dk/api/gsx/stand?callsign=XNO10&icao=EKCH&scenery=
```

FlightStrips looks up the strip for that callsign in the live session at that
airport, and answers with an arrival stand or a departure target:

```json
{ "stand": "D2", "point": null, "target": null, ... }
{ "stand": null, "point": "S1",
  "target": { "lat": 55.626033, "lon": 12.653220, "heading": null, "radius_m": 40 }, ... }
```

- **Arriving:** the script calls `selectGate()` with the stand.
- **Departing:** the script adds an **ATC Assigned** entry to the pushback menu,
  a copy of your route that ends nearest the target, within 40 m and closer
  to the assigned point than to any neighboring release point.
  - **Two facings:** where your stand has two routes ending at that point, the
    airport's facing rule for the stand picks one. Without a rule, the nearest
    route is taken.
  - **Direction buttons:** a controller assigns a bare taxiway with one, and
    the script takes your route facing that way.

The endpoint is public: GSX scripts can only make a plain GET request, with no
headers. It discloses nothing beyond what is already public on the VATSIM
datafeed. The details are in the [GSX stand feed](/dev/gsx-stand-feed/)
reference.

### Adapt it to your profile

<Steps>

1. **Name the file after your profile.** GSX loads an airport script only when
   its name is the profile's name plus `_handler`:

   | Your profile | Your script |
   | --- | --- |
   | `EKCH-Simnord-Sonnich.ini` | `EKCH-Simnord-Sonnich_handler.py` |
   | `EGKK-MyScenery.ini` | `EGKK-MyScenery_handler.py` |

   A wrong name means the script never loads, and GSX gives no warning. If you
   already ship a handler, it has this name already: paste into that file.

2. **Paste it after your own code.** The block must come last, below every
   callback your script defines. It saves the callbacks it finds above it,
   then defines its own, which call yours first:

   ```python
   # your script, unchanged
   def onAirportBeforeVehicleSelect(self):
       ...  # your operators and vehicles

   # >>> FlightStrips - generated by gsx-client/tools/embed.js, do not edit by hand >>>
   ...
   # <<< FlightStrips <<<
   ```

   This covers `onEnterAirport`, `onAirportBeforeVehicleSelect`,
   `onAirportDepartureRequested`, `onAirportBypassPinConnected`,
   `onAirportGateReset` and `onExitAirport`. A callback defined below the
   block replaces FlightStrips' own, and assignment stops working without an
   error.

3. **Check your names.** Every name in the block starts with `FS_` or
   `_stand`. Don't use either prefix in your own code: the block would replace
   it, or yours would replace the block's.

4. **Set the scenery key, usually to nothing.** Near the top of the block:

   ```python
   FS_API_BASE = "https://api.flightstrips.dk"
   FS_SCENERY = ""
   ```

   Leave `FS_SCENERY` empty unless your scenery is mapped (see
   [When to map your scenery](#when-to-map-your-scenery)); most profiles need
   no mapping. Leave `FS_API_BASE` on the production server unless your vACC
   runs its own FlightStrips instance.

5. **Change the other settings only for a reason.** They're just below the two
   above. See [Settings](#settings).

6. **Leave the rest as it is.** Everything else between the two marker lines
   is replaced when you update, so a change there is lost. If the block does
   something wrong for your profile, open an issue or a pull request against
   the FlightStrips repository instead.

</Steps>

Then [check your profile](#2-check-your-profile) and [test it](#3-test-it).

### Update to a newer FlightStrips

Replace everything from the `# >>> FlightStrips` line to the
`# <<< FlightStrips <<<` line with the new block, then set `FS_SCENERY` and any
setting you changed again.

Or let the embed tool do it, from the FlightStrips repository. It replaces the
block and keeps the `FS_API_BASE` and `FS_SCENERY` set in it:

```bash
node gsx-client/tools/embed.js path/to/EGKK-MyScenery_handler.py
```

The same command adds the block to a script that has none. `--scenery KEY` and
`--api-base URL` set those two settings, and it warns about names in your code
that clash with the block's.

### Settings

The defaults are what pilots should get. Change them only for a reason. The
shipped EKCH script uses the same names without `FS_`.

| Setting | Default | Effect |
| --- | --- | --- |
| `FS_ATC_ENTRY_LABEL` | `ATC Assigned` | The menu entry's name before a point is assigned. |
| `FS_ATC_ENTRY_LABEL_POINT` | `ATC Assigned: %s` | Its name once a point is assigned before the menu is built. Must start with `FS_ATC_ENTRY_LABEL`. |
| `FS_SHOW_ON_VDGS` | `True` | Also show `PUSH S1 FACE N` on the stand's docking display. |
| `FS_POLL_INTERVAL_MS` | `5000` | How often the script asks FlightStrips. |
| `FS_ANNOUNCE_WAITING` | `False` | Tell a pilot who calls the tug that no point is assigned yet. Off, because offline the pilot would wait for a point that never comes. |
| `FS_ATC_ENTRY` | `True` | Turn off only to fall back to the older marking modes. |

## 2. Check your profile

The audit tool reads your `.ini` and reports which release point each route
actually ends at:

```bash
node gsx-client/tools/audit.js path/to/EKCH-MyScenery.ini
```

| Flag | Meaning | Effect for pilots |
| --- | --- | --- |
| `MISLABEL` | The name says one point, the route ends at another. | The script uses it for where it goes, and shows pilots the right point. Worth renaming. |
| `NO POINT` | The name says a point, but the route ends more than 40 m from it. | The route is never offered for that point. Check its position. |
| `NO POS` | The `.ini` gives the route no position; GSX computes it in the sim. | Matched normally in the sim. The audit can't check it. |

`--all` also lists the routes that are fine. The two EKCH Simnord profiles
audit clean apart from three known mislabels and one doubtful point.

A route that ends at no release point, like `Face West`, is reachable with the
controller's direction buttons, so it needs nothing.

## 3. Test it

You can fly the whole departure flow without a controller, using the mock
server in `gsx-client/mock/`. It answers like FlightStrips and lets you play the
controller.

<Steps>

1. **Start a mock server.** On Windows, the keyboard-driven one:

   ```powershell
   powershell -ExecutionPolicy Bypass -File gsx-client\mock\api-tui.ps1
   ```

   It offers EKCH D2's four release points, with their real positions. To test
   another airport, edit the top of the script: `$Points` for the points to
   offer, and `$ConfigPath` for that airport's `gsx_sceneries.json`, where the
   positions come from. Each point needs an entry under `release_points` in that
   file. If it has none, add the point's latitude and longitude there first;
   without a position the mock has no target to send.

2. **Point your installed script at it.** This copies your script into your GSX
   folder under its own filename, and sets `FS_API_BASE`:

   ```bash
   gsx-client/mock/deploy.sh http://localhost:8787 path/to/EGKK-MyScenery_handler.py
   ```

   Leave out the second argument to deploy the EKCH script from the repository.

   Never commit a local `FS_API_BASE`. Set it back to the production URL before
   you publish.

3. **Load the script.** Start the sim at your airport with the profile active.
   To reload the script without restarting, enable handler scripts with
   `enable_handler_scripts` in `%APPDATA%\Virtuali\CouatlAddons.ini`, then press
   `F5` in GSX's Handler Script Editor.

4. **Fly the departure checks.** Park at the stand you configured the mock for,
   and run each case:

   | Assign | When | Expect |
   | --- | --- | --- |
   | A point | Before the tug is called | An announcement. The menu is untouched until pushback is requested. |
   | A point | While the tug drives out | The entry is renamed `ATC Assigned: <route>`. Picking it pushes there. |
   | A point | With the direction menu on screen | The entry is still called `ATC Assigned`. Picking it pushes to the point. |
   | A point the stand lacks | Any time | `no route to it from this stand`. |
   | Reset | After assigning | The entry goes back to the scenery's first route. |

5. **Watch the log.** Every line the script writes starts with `[stands]`, in
   `%APPDATA%\Virtuali\Couatl.log`. A route chosen by position under another
   name is logged as `S2 is "S1 Face S" at this stand, by position`. A script
   with an error is skipped with a single `WARNING: airport handler script`
   line and nothing in the sim.

</Steps>

## Publish

- Ship the script next to the `.ini`, named for it, with `FS_API_BASE` on the
  production URL.
- Link pilots to [GSX for pilots](/gsx/pilots/).

## When to map your scenery

Almost never. Pushback points need nothing from you, and facing rules belong to
the airport, so FlightStrips keeps them for every profile. Only one case is
left:

- **Your stand names don't end in the controller's name**, so GSX can't match
  `D2` to your parking by itself. One EKCH scenery calls stand F91
  `Parking 91`.

Then add your scenery to `backend/config/<icao>/gsx_sceneries.json` with a pull
request against the FlightStrips repository:

```json
{
  "gates": {
    "F91": {
      "MyScenery": { "stand": "Parking 91" }
    }
  }
}
```

The gate key is the stand as controllers know it, the scenery key is a name of
your choosing, and `stand` is what GSX's `selectGate()` resolves in your
scenery. Once merged, set `FS_SCENERY = "MyScenery"` in your script, or re-run
the embed tool with `--scenery MyScenery`.

The file also has a per-scenery `points` mapping to route labels. It only
serves handler scripts older than position matching, so leave it out.

## If you change the script

GSX constrains airport scripts in ways that fail silently. Each of these has
already cost a test flight:

- **Reads of `getGate().pushbackAddPos` are copies.** Changing a dict read out
  of it does nothing. Write the whole list back, keeping its length and order.
- **Never remove routes, or write `getGate().pushback`, and leave it that way.**
  GSX reaches "Release parking brakes" and the tug never moves. Adding an entry
  is safe.
- **Never change the routes once the aircraft is moving.** The tug is driving
  them.
- **Labels are fixed once GSX shows the direction menu,** at departure state 5.
  Where an entry leads is not: GSX reads the routes again when the tug drives.
- **Builtins are restricted.** `globals()`, `setattr`, `vars` and `delattr` are
  not available.
- **Create attributes on `self` by plain assignment.** An attribute written
  through `self.__dict__` raises "not accessible from handler scripts" when it
  is read later.
- **Use `True`, not `TRUE`.** A typo like that is reported only as one warning
  line in the log.

Run the test suite before flying, against your script or the shipped one. It
needs Python 3.7, the version GSX ships. From `gsx-client/`:

```bash
docker run --rm -v "$PWD:/w" -w /w python:3.7-alpine \
  python mock/suite.py EKCH-Simnord-Sonnich_handler.py
```
